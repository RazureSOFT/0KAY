HTTP API 参考

> Language / 语言: English · 简体中文

Core HTTP 网关的完整参考。默认基地址为 http://127.0.0.1:8080 （CORE_HTTP_PORT、CORE_BIND_HOST）。设置 CORE_LAN_ENABLED=1 后，同一组 路由会额外通过 TLS 在 https://<host>:8443 上提供。gRPC 插件协议见 PLUGIN_API。

1. 约定

认证

所有路由（包括 /health）都在同一道门后：

  • 回环（loopback）调用方以及 CORE_TRUSTED_NETWORKS 网段内的调用方视为可信，

无需凭据。

  • 其他调用方必须出示以下之一：Authorization: Bearer <token>（配对设备令牌

或 CORE_API_TOKEN），或由 POST /api/auth/session 签发的 HttpOnly 0kay_session Cookie。

  • 失败返回 401，带 WWW-Authenticate: Bearer realm="0kay" 以及 code 为

unauthenticated 的 JSON 错误信封。

  • 配置了访问 PIN 后，敏感路由还要求 PIN（X-0kay-Pin 请求头，或 pin:

会话 Cookie）。PIN/令牌失败按客户端限速：5 次失败锁定 15 分钟，返回 429 too_many_attempts 与 Retry-After。

/api/auth/session 在这道门之前运行，未认证的浏览器可以先探测是否需要凭据 并提供凭据：

方法路径用途
GET, HEAD/api/auth/session{authenticated, method, requires_auth, core_id, lan_enabled}
POST/api/auth/session{token} → 设置 0kay_session（HttpOnly，SameSite=Strict，30 天）→ {authenticated, method:"cookie", requires_auth, core_id}
DELETE/api/auth/session清除 Cookie → {authenticated:false, method:""}

Cookie 的值就是 bearer 令牌本身，因此只要浏览器这一跳是加密的就会带上 Secure：直连 TLS，或可信对端（TLS 终结的反向代理）传入的 X-Forwarded-Proto: https。无法推断部署形态时可用 CORE_COOKIE_SECURE=1|0 强制覆盖。

插件配对回调（/api/pairing/*）在这道门之前处理，并应用自己的 loopback/Origin 规则。

Host 与 Origin 校验

  • DNS 重绑定防护：回环、IP 字面量与单标签主机名（如 compose 服务名 core）

直接接受；其他主机必须出现在 CORE_ALLOWED_HOSTS / CORE_ALLOWED_ORIGINS 中，或由 pairingHostIdentity() 上报，否则返回 403 host_not_allowed。 两个变量里的条目可以是裸主机名、host:port 或完整 origin URL，Host 校验 时都会归约为主机名。CORS 授权则要求 CORE_ALLOWED_ORIGINS 条目必须是完整 origin（协议、主机、非默认端口），与浏览器的 Origin 头精确匹配。

  • 允许的 origin：同源、localhost/127.0.0.1 各变体，以及

CORE_ALLOWED_ORIGINS（逗号分隔）中列出的主机。其余 origin 返回 403 origin_not_allowed。

  • 允许的方法：GET, POST, PUT, PATCH, DELETE, OPTIONS。允许的头：

Content-Type, Authorization。

  • 被接受的 origin 会通过 Access-Control-Allow-Origin、

Access-Control-Allow-Credentials: true 和 Vary: Origin 回显。

  • OPTIONS 预检在令牌校验之前返回 204 空响应体。

安全相关环境变量

变量作用
CORE_API_TOKEN所有 /api/* 路由接受的共享 bearer 令牌。
CORE_PIN首次运行时播种 6 位访问 PIN（否则自动生成并打印到日志）。
CORE_COOKIE_SECURE强制会话 Cookie 的 Secure 标志开（1）或关（0）；缺省由 TLS / 可信代理的 X-Forwarded-Proto 推断。
CORE_TRUSTED_NETWORKS逗号分隔的 CIDR，视同回环（无需逐请求凭据）。
CORE_ALLOWED_HOSTS、CORE_ALLOWED_ORIGINSHost / DNS 重绑定与 CORS 白名单。
CORE_PLUGIN_REGISTRATION_TOKEN可选的共享注册密钥：每个非内置插件在 gRPC 注册时必须出示（x-0kay-registration-token 元数据）。
CORE_SSRF_STRICT1 时对模型拉取与插件出口代理额外封禁 loopback/RFC1918；metadata/链路本地/CGNAT 永远封禁。

错误

除 SSE 响应体（错误以 event: error 上报）外，所有失败使用同一信封，恒为 application/json：

{"error": "human readable message", "code": "machine_code"}

error 保持字符串，既有的 data?.error 客户端不受影响。方法不匹配返回 405 与 Allow。常见 code：bad_request、unauthenticated、forbidden、 not_found、method_not_allowed、section_disabled、upstream_error、 unavailable、host_not_allowed、origin_not_allowed、cross_site_denied、 machine_credential_required（403，浏览器会话访问机器专用端点）、 pin_required、too_many_attempts（429，PIN/令牌锁定）、 plugin_identity_required、api_not_permitted。

POST /api/usage/record 成功时仍返回 204 空响应体。

请求细节

  • JSON 请求体使用 snake_case 字段名与 Content-Type: application/json。
  • 服务端按路由强制请求体上限（超限在解码前拒绝）：chat/LIFE chat 4 MB，

直接运行类（/api/run、审批、提问、workspace、host、compact）64 KB， agent 消息 128 KB，通用小请求体（settings、providers、models、skills 删除） 64 KB，skills POST 2 MB，tasks 2 MB，images 16 MB（每个 multipart 分片 8 MB），files 64 MB（每分片 16 MB），live2d 上传 512 MB（每分片 32 MB）。

  • 常用查询参数：?limit= ?query= ?cursor= ?incremental=1

?session_id= ?executor_id= ?path= ?id= ?name= ?values=1 ?file=。

弃用

旧别名路由继续可用，并返回

Deprecation: true
Link: </api/usage>; rel="successor-version"

指向后继路由，例如 POST /api/usage/clear → DELETE /api/usage、 POST /api/plugins/enable → PATCH /api/plugins/{name}。

8. 对话与模型

POST /api/chat（别名 POST /api/mocr/generate）

{"request_id": "r1", "prompt": "hi", "stream": false,
 "session_id": "default", "model_id": "", "system_prompt": "",
 "temperature": 0.7, "max_tokens": 1024,
 "messages": [{"role": "user", "content": "hi"}]}
  • stream: false → {"request_id", "response", "error"?, "usage"?: {prompt_tokens, completion_tokens, total_tokens}}
  • stream: true → SSE event: chunk / event: done / event: error。

空 model_id 表示走 Core/mocr 选型（MOCR）；固定模型 id 可绕过选型。

Core 总是向 mocr 请求流式生成并自行聚合分片，请求里的 stream 只决定 HTTP 响应形态。上游失败——包括流结束却没有显式 done——会变成真实错误（JSON 形式返回 502，SSE 形式发 event: error），而不是静默的空回答。

POST /api/life/chat

WebUI 主对话路径；把 LIFE 的 OnUserMessage 代理为 SSE。

{"request_id": "life_1", "session_id": "webui:default", "user_id": "webui",
 "prompt": "…", "persona": {}, "history": [],
 "attachments": [{"name": "report.pdf", "url": "/api/files?file=file_2.pdf",
                  "mime": "application/pdf", "size": 1024}]}

attachments（来自 POST /api/files）会以 <attachments>…</attachments> JSON 标记追加进 prompt。LIFE 从 Core 拉取每个文件并转成多模态模型内容—— 文本内联、图片作为原生图像分片（主模型拒收图片时回退到配置的视觉模型）—— 然后移除标记。存在至少一个附件时 prompt 可以为空。

persona 可包含 customPrompt，LIFE 会把它作为 system prompt 发给模型。 分片载荷：{request_id, chunk, done, task_id, think_summary, emotion: {valence, arousal, connection, irritation}, mental_energy}。事件： chunk、done、error（LIFE 离线时 503 LIFE is unavailable）。

供应商配置持久化到 data/providers.json。存储初始化期间返回 503 provider store not ready。

每个供应商行可带 format 字段，独立于 provider 预设选择线上协议： "openai"（/chat/completions）或 "anthropic"（/v1/messages）。留空表示 *自动*——mocr 根据预设名或 anthropic.com 的 base_url 推断。这样 custom （或任何以 OpenAI 命名的）端点也能说 Anthropic Messages 协议，例如 Claude 兼容中转。Core 把生效后的 provider 传给 mocr 和 /api/providers/credentials，LIFE / Agent / mocr 据此选择正确的传输；脱敏的 /api/providers 视图保留原始预设与 format 供展示。

API key 永远不会通过 /api/providers 离开 Core。 列表是脱敏的： api_key 为空，api_key_masked 形如 abcd************wxyz（前 4 位 + 12 个 * + 后 4 位；≤8 字符的 key 全遮蔽）。upsert 时回传空或遮蔽的 api_key 会保留已存密钥，遮蔽值永不落盘。只有 GET /api/providers/credentials 返回明文，且仅限机器调用方：请求必须带 有效的插件身份（X-0KAY-Plugin + 服务令牌）或配对设备 / CORE_API_TOKEN bearer。浏览器会话 Cookie 不够——即便同源也不行——所以同源的插件 WebUI bundle 读不到 key（403 machine_credential_required）。跨站读取先被拒绝 （Sec-Fetch-Site: cross-site → 403 cross_site_denied）。它的存在是为 仓库内的服务（LIFE / Agent / mocr）向上游转发密钥。

供应商模型拉取（POST /api/models/fetch）与插件出口代理 （POST /api/net/egress）经过 Core 的 SSRF 防护：链路本地/metadata、 CGNAT/保留段、以及（CORE_SSRF_STRICT=1 时）loopback/内网目标都会被拒绝， 每个重定向都会重新校验。

POST /api/models/fetch 在服务端解析密钥：api_key 为空或被遮蔽时按 id、 再按 (provider, base_url) 查找。遮蔽的 key 永远不会转发给供应商的模型端点。

stdio 托管的供应商插件

manifest 声明了 provider 块的包（见 PLUGIN_API.md §0.1.3），其供应商由 Core 以 stdio 子进程托管——不占用插件端口。Core 在启动时拉起声明的命令，以 base_url = http://127.0.0.1:<core-http-port>/api/stdio-provider/<id><route> 注册供应商，并通过 stdin/stdout 的换行分隔 JSON 转发每个请求。

方法路径用途
GET, POST/api/stdio-provider/{id}/{path…}代理到 stdio 托管的供应商 id（如 /api/stdio-provider/opencode-free/v1/chat/completions）

供应商模型来自 manifest 的 models 列表；缺省时从子进程的 GET <route>/models 发现。注册在后台运行，慢子进程不会阻塞 Core 启动。 安装了声明 provider 的包之后需要重启 Core。

17. 内置搜索

Core 自带网页搜索（没有 SearXNG 插件或额外端口）；Agent 与 L.I.F.E. 调用 这些路由。三者都接受 GET ?q=&n=（别名 ?query=）或 POST {"query":"…","n":10}，返回相同信封 {query, results:[{title,url,snippet,engine}], errors:[…]}。搜索失败记录在 errors 里（绝不抛硬 5xx）：结果偏少仍是 200。

方法路径用途
GET, POST/api/search网页搜索；`?engine=cnbing\bing\so360\duckduckgo（默认取 search` 设置节）
GET, POST/api/search/papers学术文献（arXiv / Crossref / OpenAlex）
GET, POST/api/search/apidocsAPI 文档（MDN / Microsoft Learn / Stack Overflow），带文档域过滤的网页兜底

结果按 URL 去重并按来源优先级交错；n 默认 10（专用后端为 8），上限 50。
